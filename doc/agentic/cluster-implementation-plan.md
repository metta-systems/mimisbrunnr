# Cluster support — implementation plan

Design: [cluster-design.md](cluster-design.md) · Decisions: [cluster-decisions.md](cluster-decisions.md) · Order: [operations-plan.md](operations-plan.md)

Prerequisites for the whole scope: [SNAPSHOT6](snapshots-implementation-plan.md), [RECONCILE2](reconcile-implementation-plan.md).

## State and changes

- [ ] **CLUSTER1 — Peer records.** The `ClusterPeers` tree of `PeerRecord`s (CLUSTER-DESIGN§2) with the cursor type CLUSTER-D7 selects, and the peer operations of CLUSTER-DESIGN§5. Prerequisites: CLUSTER-D1, CLUSTER-D7. Acceptance: peer records and their cursors round-trip through reopen; a crash after an acknowledgement and before the next checkpoint replays to the same cursor.
- [ ] **CLUSTER9 — Change export.** Export for a peer from its cursor in bounded batches, each with the cursor it reaches, read from the direct-state trees and skipping blocks by snapshot range (CLUSTER-DESIGN§1), selected as CLUSTER-D7 decides; acknowledgement advances the cursor. Prerequisites: CLUSTER1, CLUSTER-D7, [BTREE9](btree-implementation-plan.md) (block snapshot ranges). Acceptance: an export after 10 tag changes on a 1 M-object pool holds 10 object changes and reads only the blocks holding them (counted); an export interrupted after any batch resumes from the last acknowledged cursor and yields the same total.
- [ ] **CLUSTER2 — Apply and merge.** Applying a batch journals its changes as local mutations with their origin timestamps, merging objects changed on both sides by the rules CLUSTER-D2 selects and collection order by CLUSTER-D6; constraint violations are reported. Prerequisites: CLUSTER9, CLUSTER-D2, CLUSTER-D6. Acceptance: concurrent edits of one object's tags on two nodes converge to the same state on both; applying the same batch twice leaves the state of the first application.
- [ ] **CLUSTER7 — No local ids in exports.** Changes name tags by `TagUid` and terms by value, never by `TagId` or `TermId`; applying interns them into the local dictionary, and no postings or derived terms are exported. Prerequisites: CLUSTER9, [INDEX12](index-implementation-plan.md). Acceptance: two nodes with independently created pools converge on an attribute and a tag although their local ids differ.
- [ ] **CLUSTER8 — Ontology by uid.** An export lists the ontology records changed since the cursor, by uid, ahead of object changes; applying allocates `TagId`s for tags new to the node and reworks postings (ONTOLOGY-DESIGN "Cluster propagation"); concurrent edits merge by union of provenance, scalar fields last-writer-wins by hybrid timestamp. Prerequisites: CLUSTER9, [ONTOLOGY10](ontology-implementation-plan.md). Acceptance: a module installed on one node, then an object tagged with its tag, arrive on another node in that order and the tag resolves there.

## Content

- [ ] **CLUSTER10 — Chunk transfer with durable progress.** The content operations of CLUSTER-DESIGN§5: an object's chunk list; reading a stored chunk by hash or by key; recording a chunk list as absent chunks (CLUSTER-DESIGN§3, `CHUNK_FLAG_ABSENT` entries with no replicas); storing a fetched chunk after its hash verifies, or deduplicating it onto a local copy with the same hash; listing the chunks still lacking; peer choice as CLUSTER-D10 selects. Prerequisites: [METADATA8](metadata-implementation-plan.md), [BLOB3](blob-implementation-plan.md), CLUSTER-D10. Acceptance: a 1 GiB object transferred between two pools through a test cluster manager, killed after half its chunks are stored, resumes on reopen fetching only the absent half and ends byte-exact with its hash; a chunk whose bytes do not match its hash is refused and stays absent; a chunk the receiver already holds under the same key is stored without being fetched and names the existing replicas; every stored chunk gets the replica count its policy asks for.
- [ ] **CLUSTER11 — Transfer records.** The `Transfers` tree of `TransferRecord`s (CLUSTER-DESIGN§4): inbound records created by the filesystem for opens of remote content, hydration and pin rules and resilver, with progress advanced in the commit that stores each chunk and recomputed at mount; outbound records and reported progress; the transfer operations of CLUSTER-DESIGN§5. Read access for applications as CLUSTER-D11 selects. Prerequisites: CLUSTER10. Acceptance: a transfer's `chunks_done` never exceeds the object's present chunks, including after a crash between a chunk store and the next checkpoint; pausing, resuming and cancelling change state and survive reopen; listing transfers by state returns them in priority order.
- [ ] **CLUSTER5 — Partially present content.** Reads and records of objects with absent chunks as CLUSTER-D3 selects, including stubs kept by hydration rules. Prerequisites: CLUSTER-D3, CLUSTER10.

## Verification

- [ ] **CLUSTER6 — Multi-node convergence suite.** A test cluster manager drives two and three in-process nodes through: concurrent edits; one node offline for a long run of changes on both sides, then rejoining; a cluster-manager crash mid-export and mid-transfer; a node crash mid-transfer; a peer relaying another's changes. Every scenario ends with converged direct state, no change lost on either side, and transfers resumed rather than restarted. A node answers a tag query for an object it did not write without fetching content ([acceptance scenarios](operations-design.md#acceptance-scenarios); evidence kind `L4`). Prerequisites: CLUSTER2, CLUSTER11.
