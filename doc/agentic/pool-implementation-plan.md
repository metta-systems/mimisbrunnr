# Pool management — implementation plan

Design: [pool-design.md](pool-design.md) · Decisions: [pool-decisions.md](pool-decisions.md) · Order: [operations-plan.md](operations-plan.md)

- [ ] **POOL1 — More disks than the inline descriptor slots.** `PoolManager` rejects pools beyond the inline limit with `PoolError::DiskOverflowUnsupported` (`crates/pool/src/pool.rs`); route the extra descriptors through the `disks_overflow` tree. Acceptance: a pool with more disks than the inline slots creates, reopens and lists every disk.
- [ ] **POOL2 — Ontology-driven placement end to end.** An ontology rule attached to a tag (for example `archive` implies cold tier) moves matching objects without a separate user action. Prerequisites: [BLOB1](blob-implementation-plan.md), [RECONCILE5](reconcile-implementation-plan.md), [TOOLING3](tooling-implementation-plan.md), POOL4. [Acceptance scenario](operations-design.md#acceptance-scenarios).
- [ ] **POOL3 — Pool state through the root pointer.** Locate `PoolStateRoot` through `RootPointer.pool_state_root` instead of the hard-coded `POOL_STATE_ROOT_OFFSET` (block 4) in `crates/pool/src/tier.rs`. Acceptance: a pool whose state block is written elsewhere reopens through the root pointer.
- [ ] **POOL4 — Placement-rule evaluator.** `PoolManager::pick_disk` resolves rules in SPECIFICATION-DESIGN§8.3 precedence (Pin > Prefer > Replicate > AutoTier > defaults) instead of the current disk-level pick. Acceptance: one test per precedence level, plus a conflict between two levels resolved by precedence.
- [ ] **POOL5 — Native placement-rules tree.** Persist placement rules as one sorted-run entry per rule keyed `(rule_id, snapshot)` (POOL-DESIGN§1) instead of a single CBOR entry holding the whole list; each value is the positional, versioned rule SPEC25 pins in POOL-DESIGN§1, with its query through QUERY11. Prerequisite: [QUERY11](query-implementation-plan.md). Acceptance: adding one rule appends one entry; rules round-trip through reopen; a newer schema version fails with a defined `PoolError`.
- [ ] **POOL6 — Disk evacuation on removal.** `remove_disk` range-scans the disk's backpointers to find the objects with data on it, re-evaluates placement, migrates extents, and only then marks the disk `Removed` (SPECIFICATION-DESIGN§8.4); today it only marks it `Draining`. Prerequisites: POOL4, [BLOB1](blob-implementation-plan.md), [ENGINE5](engine-implementation-plan.md). Acceptance: removing a disk in a two-disk pool leaves every object readable from the remaining disk.
- [ ] **POOL7 — Pool assembled from its devices.** Pool membership and identity live only on disk: each member's superblock (`fs_uuid`, `disk_id`, `node_id`) and the `PoolStateRoot` disk descriptors. `PoolManager::open` takes a set of `BlockDevice`s, groups them by `fs_uuid`, checks every descriptor's disk is present and refuses a missing or foreign disk with a defined error; nothing names a host path. A device may be a byte range of a larger device (a partition, or a partition inside an image file). `PoolConfig`, `pool.toml` and the `toml` dependency of `crates/pool` go away; `brunnr` and `mimir` take device or image paths (with an optional partition offset) instead of `--pool <pool.toml>`, and the `Justfile` recipes follow. Prerequisite: POOL3. Acceptance: a two-disk pool on image files reopens from its two paths given in either order; a pool inside the second partition of an image reopens from the image path and partition; dropping a disk or adding one from another pool fails with the defined error; no `pool.toml` remains in `crates/`, `bin/` or the `Justfile`.
