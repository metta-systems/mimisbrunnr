# Pool management — implementation plan

Design: [pool-design.md](pool-design.md) · Decisions: [pool-decisions.md](pool-decisions.md) · Order: [operations-plan.md](operations-plan.md)

- [ ] **POOL1 — One disk-descriptor tree.** Every disk's `DiskDescriptor` (POOL-DESIGN§1.1: disk UUID, no host path, `NodePtr` allocation roots) lives in the `DiskDescriptors` tree whatever the disk count; the inline array, `PoolError::DiskOverflowUnsupported` and the overflow mode go (`crates/pool/src/pool.rs`). Prerequisite: [ALLOCATION9](allocation-implementation-plan.md). The descriptor holds media class, tier, state and a `bucket_count` copy of capacity, and no `first_usable_bucket`. Acceptance: pools of 1 and 20 disks create, reopen and list every disk; the descriptor layout is asserted; with one disk missing, `brunnr status` reports its capacity from the descriptor; a device whose geometry disagrees with its descriptor's `bucket_count` fails to open with a defined error; changing a disk's tier rewrites no superblock.
- [ ] **POOL2 — Ontology-driven placement end to end.** An ontology rule attached to a tag (for example `archive` implies cold tier) moves matching objects without a separate user action. Prerequisites: [BLOB1](blob-implementation-plan.md), [RECONCILE5](reconcile-implementation-plan.md), [TOOLING3](tooling-implementation-plan.md), POOL4. [Acceptance scenario](operations-design.md#acceptance-scenarios).
- [ ] **POOL3 — Pool state record through the root list.** The `PoolStateRecord` (POOL-DESIGN§1.2) in its single-entry `PoolState` tree, reached through the root list, replaces the `PoolStateRoot` block at the hard-coded `POOL_STATE_ROOT_OFFSET` (block 4) in `crates/pool/src/tier.rs`. Prerequisites: [SPEC25](specification-implementation-plan.md), [ENGINE12](engine-implementation-plan.md). Acceptance: fixed expected bytes for the record; tunables and the error log survive reopen; a newer schema version fails with a defined `PoolError`.
- [ ] **POOL4 — Placement-rule evaluator.** `PoolManager::pick_disk` resolves rules in SPECIFICATION-DESIGN§8.3 precedence (Pin > Prefer > Replicate > AutoTier > defaults) instead of the current disk-level pick, matching each rule's query through `matches` ([QUERY16](query-implementation-plan.md)); rules are registered as watchers in the match index ([SUBSCRIPTION3](subscriptions-implementation-plan.md)), so a retag reaches only the rules its closure delta touches. Acceptance: one test per precedence level, plus a conflict between two levels resolved by precedence; tagging an object `archive` under a `Pin { archive → cold }` rule enqueues exactly one reconcile entry for it, and a mutation touching no rule's terms enqueues none; a rule with `size > 1 GiB` matches as `mimir query` does.
- [ ] **POOL5 — Native placement-rules tree.** Persist placement rules as one sorted-run entry per rule keyed `(rule_id, snapshot)` (POOL-DESIGN§1) instead of a single CBOR entry holding the whole list; each value is the positional, versioned rule SPEC25 pins in POOL-DESIGN§1, with its query through QUERY11. Prerequisite: [QUERY11](query-implementation-plan.md). Acceptance: adding one rule appends one entry; rules round-trip through reopen; a newer schema version fails with a defined `PoolError`.
- [ ] **POOL6 — Disk evacuation on removal.** `remove_disk` range-scans the disk's backpointers to find the objects with data on it, re-evaluates placement, migrates extents, and only then marks the disk `Removed` (SPECIFICATION-DESIGN§8.4); today it only marks it `Draining`. Prerequisites: POOL4, [BLOB1](blob-implementation-plan.md), [ENGINE5](engine-implementation-plan.md). Acceptance: removing a disk in a two-disk pool leaves every object readable from the remaining disk.
- [ ] **POOL8 — Administrative changes commit by checkpoint.** `brunnr` commands that change the pool state record, disk descriptors, placement rules or cluster peers apply the change and force a checkpoint before returning, with no journal op (POOL-DESIGN§1.2). Prerequisites: POOL3, [JOURNAL12](journal-implementation-plan.md). Acceptance: a placement rule added and acknowledged survives a kill immediately after; a kill injected before the forced checkpoint leaves the pool without the rule and otherwise unchanged.
- [ ] **POOL7 — Pool assembled from its devices.** Pool membership and identity live only on disk: each member's superblock (`fs_uuid`, `disk_uuid`, `disk_id`, `node_id`) and the disk descriptors (POOL-DESIGN§1.1). `PoolManager::open` takes a set of `BlockDevice`s, groups them by `fs_uuid`, checks every descriptor's disk is present and refuses a missing or foreign disk with a defined error; nothing names a host path. A device may be a byte range of a larger device (a partition, or a partition inside an image file). `PoolConfig`, `pool.toml` and the `toml` dependency of `crates/pool` go away; `brunnr` and `mimir` take device or image paths (with an optional partition offset) instead of `--pool <pool.toml>`, and the `Justfile` recipes follow. Prerequisites: POOL1, POOL3. Acceptance: a two-disk pool on image files reopens from its two paths given in either order; a pool inside the second partition of an image reopens from the image path and partition; dropping a disk or adding one from another pool fails with the defined error; no `pool.toml` remains in `crates/`, `bin/` or the `Justfile`.
