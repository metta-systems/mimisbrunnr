# Ontology — implementation plan

Design: [ontology-design.md](ontology-design.md) · Decisions: [ontology-decisions.md](ontology-decisions.md) · Order: [operations-plan.md](operations-plan.md)

## Records and identity

- [ ] **ONTOLOGY2 — `OntologyError::Storage`.** Add `Storage(#[from] StorageError)` and replace the lossy mapping of region errors into `OntologyError::Cbor`. Acceptance: a region-full failure surfaces as the storage variant in a test.
- [ ] **ONTOLOGY10 — Per-record ontology tree.** The `Ontology` tree keyed `(record_kind, a, b, snapshot)` with `TagRecord`, `RuleRecord` and `ModuleRecord` as ONTOLOGY-DESIGN§1 pins (positional, versioned, `Value` and storage policies through the `crates/types` codec); mount loads every record and builds the name maps, uid ↔ `TagId` maps and closure tables. Replaces `OntologyImage` and its derived `Serialize`. Prerequisites: [SPEC25](specification-implementation-plan.md), [INDEX9](index-implementation-plan.md). Acceptance: fixed expected bytes for one record of each kind and rule kind; tags, rules and modules round-trip through reopen; a newer schema version fails with a defined `OntologyError`; creating one tag rewrites one tree entry.
- [ ] **ONTOLOGY1 — Single tag-id allocator, ad-hoc tags in `local`.** `Engine.next_tag_id` goes; every tag, ad hoc or from a module, gets its `TagId` from `next_tag_id` in the root list head (ENGINE-DESIGN§1.2), and ad-hoc tags are records with a random `TagUid` and the `local` module in their provenance. Prerequisite: ONTOLOGY10. Acceptance: tags registered ad hoc and through modules never collide across reopen; removing the tag with the largest `TagId`, reopening and creating a tag yields a larger id; `Engine::register_tag` writes a record with `local` provenance ([ENGINE7](engine-implementation-plan.md)).
- [ ] **ONTOLOGY15 — Tag uids and name resolution.** `TagUid` derivation (BLAKE3 over module id and name, random for `local`), canonical names, aliases and qualified names (`module:name`); an ambiguous unqualified name fails with an error listing the candidates. Prerequisite: ONTOLOGY10. Acceptance: the uid of a module tag is identical across nodes and module versions; two modules declaring `album` both install, `album` alone is ambiguous, each qualified name resolves; an alias resolves to its tag.
- [ ] **ONTOLOGY11 — Ontology journal ops.** `OntologyPut` and `OntologyDelete` (JOURNAL-DESIGN§1.3) carry every ontology change; a module install is one commit of them; `rules_epoch` advances only on rule and constraint changes, and only then are closure tables rebuilt. Prerequisites: ONTOLOGY10, [JOURNAL8](journal-implementation-plan.md). Acceptance: a crash after an install's entries and before checkpoint replays to the same records and postings; creating and renaming tags never rebuilds closure tables (counted in the test).

## Kinds, rules and constraints

- [ ] **ONTOLOGY16 — Attribute flavours and key options.** `collection` (plain, grouping, ordered, ranked), `hierarchy_sep` and `ngram` on attribute keys, validated on assertion (ordered and ranked keys maintain sequences, INDEX-DESIGN§3.3). Prerequisites: ONTOLOGY10, [INDEX15](index-implementation-plan.md). Acceptance: a value of the wrong type for its key fails with a defined error; a playlist key with `ordered` keeps member order across reopen.
- [ ] **ONTOLOGY6 — Derived postings for new rules.** Installing or upgrading to a rule (`Implies`, `ValueImplies`, `Bucket`) posts its derived terms (INDEX-DESIGN§2.4) in the commit that installs it and rebuilds the closure tables when the estimated work is at most `rule_rework_inline_max`; above it the rule commits as `installing` and a resumable rework scan posts window by window, writes meanwhile apply the pending rule, and the last step activates it; removals likewise through `removing`; `SnapshotCreate` fails while any rule is pending; forward entries are untouched. Prerequisites: [INDEX14](index-implementation-plan.md), [RECONCILE9](reconcile-implementation-plan.md). Acceptance: with the limit forced to zero, installing `flac → audio` over 200 000 `flac` objects completes over many steps, a query of `audio` mid-way returns a subset that only grows, an object tagged `flac` mid-way is in `audio` at once, a snapshot request mid-way fails with the defined error, and the final result and a reopen both equal the one-commit install; a crash mid-rework resumes from the scan cursor to the same result; installing `lang = rust → kind = source` makes `kind = source` match every Rust file without a forward-entry change, and a `ValueImplies` on `kind = source` matches only objects asserting it directly; tag 3 objects `flac`, install `flac → audio`, query `audio` returns them, also after reopen; install `mime = audio/flac → flac` and an object with that `mime` is `audio`; install a monthly `Bucket` on `created_ns` and `created-month = 2026-11` finds the month's objects.
- [ ] **ONTOLOGY7 — Withdraw derived postings for removed rules.** Removing a rule (upgrade or module removal) withdraws what it alone derived, by INDEX-DESIGN§2.4's suspect algorithm, reading forward entries of suspects only. Prerequisite: ONTOLOGY6. Acceptance: an object tagged `flac` and `mp3` keeps `audio` after `flac → audio` is removed; one tagged only `flac` loses it and `audio`'s ancestors; a directly tagged `audio` object keeps it; removing a `ValueImplies` withdraws its tag from exactly the objects with that value and no other source; the number of forward entries read equals the number of suspects.
- [ ] **ONTOLOGY12 — Constraints.** `Exclusive` with the write behaviour ONTOLOGY-D9 selects; `Requires` rejects the assertion with a defined error; both are checked against the derived closure after the mutation; installing a constraint reports existing violators without changing them; changes applied from a peer's export or an import are accepted and their violations reported (ONTOLOGY-DESIGN "Rules and constraints"). Prerequisites: ONTOLOGY6, ONTOLOGY-D9. Acceptance: an applied batch asserting `lossless` on an object before the batch that makes it `audio` applies, reports one violation, and the report clears when the second batch lands; tagging a `current` artifact `stale` behaves as ONTOLOGY-D9 selects; asserting `Requires(lossless, audio)`'s `lossless` on a non-audio object fails and leaves the object unchanged; installing an `Exclusive` over two tags already on one object lists that object.
- [ ] **ONTOLOGY17 — Record fields and system labels.** The core ontology declares the record fields `size`, `created`, `modified`, `changed` (`TagRecord` kind 2 with `record_field`) and the system labels `_object`, `_presence:remote`, `_writing` (`flags` bit 0); `Bucket` rules accept record fields as input, and a content write moves the object between bucket terms (INDEX-DESIGN§2.4). Prerequisites: ONTOLOGY6, [METADATA7](metadata-implementation-plan.md). Acceptance: a monthly `Bucket` on `modified` finds the month's objects, and rewriting an object's content next month moves it; a module declaring a record field or system label fails to install; with `ValueImplies { size-class = huge → large-file }`, growing an object's content into `huge` adds `large-file` and shrinking it removes it; a `Bucket` whose key is another `Bucket`'s `out_key` fails to install with a defined error; with a daily `Bucket` on `changed`, retagging an object on a later day moves it to that day's bucket without rewriting its record.

## Modules

- [ ] **ONTOLOGY14 — Host-compiled modules.** A host-side compiler turns module source into the record form plus a `ModuleRecord` with the compiled form's BLAKE3 digest; the engine installs compiled modules without parsing source; install follows ONTOLOGY-DESIGN "Install" steps 1–7 as one commit, with `installers` and `core` in the module record. Prerequisites: ONTOLOGY11, ONTOLOGY15. Acceptance: a compiled module installs in a test without the source parser linked; a second installer adds itself and changes nothing else; a reference to an uninstalled tag or a rule cycle fails the install and leaves the ontology unchanged; a `core` module cannot be removed.
- [ ] **ONTOLOGY18 — Rework cost measurements.** A benchmark of rule-change rework on pools of 1 M and 10 M objects: a new `Implies` from a tag on most objects, a `Bucket` on a key with one distinct value per object, an `Implies` removal with many suspects, and an `Exclusive` install; reports the work estimate, wall time on NVMe and HDD, steps and commits for each. Feeds the default of `rule_rework_inline_max` and [SNAPSHOT-D1](snapshots-decisions.md). Prerequisite: ONTOLOGY6. Acceptance: the report lists all four cases on both pool sizes.
- [ ] **ONTOLOGY5 — Upgrade diff.** An upgrade diffs the compiled forms by uid (ONTOLOGY-DESIGN "Upgrade"): additions applied, unused tag removals applied, removals of carried tags and changes of kind, value type or collection flavour blocked with a report. Prerequisite: ONTOLOGY14. Acceptance: a test upgrades a module that changes `bpm` from `int` to `text`, expects the blocked report and an unchanged ontology; a rename with the old name as alias keeps queries by the old name working.
- [ ] **ONTOLOGY8 — Upgrade with blocked changes.** Blocked upgrade changes report object counts and migration plans and apply only with `--force`. Prerequisites: ONTOLOGY5, ONTOLOGY7, ONTOLOGY-D6.
- [ ] **ONTOLOGY9 — Scrub policies.** Module removal takes provenance out of every declaration and applies a policy: Preserve (default; tags with empty provenance become orphans), RemoveUnique, Purge; rules with empty provenance are removed under every policy. Prerequisites: ONTOLOGY7, ONTOLOGY14, ONTOLOGY-D6. Acceptance: one test per policy checks the ontology and the tagged objects after reopen; a tag declared by two modules survives RemoveUnique of one.
- [ ] **ONTOLOGY3 — Adopt orphan tags.** `mimir ontology adopt <tag> --into <module>` adds the module to an orphan's provenance. Prerequisite: ONTOLOGY9. Acceptance: an adopted orphan is no longer listed by `orphans` and survives Preserve removal of the adopting module's previous owner.
- [ ] **ONTOLOGY4 — Module syntax migration.** Prerequisite: ONTOLOGY-D2 selecting a change.
- [ ] **ONTOLOGY20 — Module dependencies and shared tags.** `ModuleRecord.requires` with semver requirements, checked at install, at a dependency's upgrade and at removal (reverse-dependency order); a module re-declaring a foreign tag by qualified name joins its provenance when the definition matches (ONTOLOGY-DESIGN "Modules"). Prerequisites: ONTOLOGY14, ONTOLOGY15. Acceptance: installing a module whose dependency is missing or out of range fails with a defined error naming it; upgrading a dependency past a dependent's range fails; removing a required module fails until its dependents are removed; two modules declaring the same qualified tag both appear in its provenance, removing either leaves the tag, and a mismatched re-declaration (different value type) fails to install.
- [ ] **ONTOLOGY19 — Rework the example modules to intersecting categories.** The software-development example (ONTOLOGY-DESIGN "Example module") and its summary in SPECIFICATION-DESIGN§13 model file roles as an implication tree of labels; rework them to the associative model (ONTOLOGY-DESIGN "Rules and constraints", intersecting categories): roles as values of a repeatable attribute the module names, `Implies` and `ValueImplies` (including into attribute values) only for genuine "every X is a Y" facts, and the example queries rewritten to intersect. The §13.2 implication-tree diagram is replaced. The unix-interop module's path conventions (UNIX-DESIGN "Import") follow the same model. Acceptance: every example query in both documents is expressible against the reworked module, and none relies on an ordering between categories.
