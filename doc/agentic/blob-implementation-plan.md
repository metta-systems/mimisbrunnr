# Blob storage and content paths — implementation plan

Design: [blob-design.md](blob-design.md) · Decisions: [blob-decisions.md](blob-decisions.md) · Order: [operations-plan.md](operations-plan.md)

## Write and read

- [ ] **BLOB1 — Non-chunked write path.** Allocate a blob bucket, append, set the record's `Extent` locator (METADATA-DESIGN§1.2), journal `WriteBlob` with the real extent (today `BlockRef::ZERO`), record the backpointer. Prerequisites: [ENGINE3](engine-implementation-plan.md), [METADATA7](metadata-implementation-plan.md).
- [ ] **BLOB2 — Read path.** `DiskEngine::read_blob` reads the bytes the record's locator names and inverts the transform; `mimir project export` works. Prerequisite: BLOB1.
- [ ] **BLOB3 — Chunked write and read.** Drive the chunked-object journal ops and the shared `ChunkList` tree keyed `(oid, end_offset, snapshot)`, with the `ChunkParamsRecord` in the locator (INDEX-DESIGN§4.3); re-chunking by `ChunkListReplace` windows. Prerequisites: BLOB2, [BTREE4](btree-implementation-plan.md). Acceptance: a 16 MiB FastCDC object round-trips through write, flush, reopen, read; a read at offset `x` seeks one key; replacing a 4 KiB range re-chunks only the chunks it touches; re-chunking with new parameters reads back byte-exact after every window and ends with the new `ChunkParamsRecord` in the locator; after a snapshot, an edit leaves the snapshot's recipe unchanged and frees none of the chunks the snapshot still uses, and deleting the snapshot then frees exactly those no key names; a write into a window during its re-chunk makes that window redo and the object reads back with the write; turning chunking on for a 100-extent object and off again reads back byte-exact after each switch, with no mix of extent and chunk keys visible at any commit.
- [ ] **BLOB4 — Selective chunking.** The write path consults the resolved storage policy (SPECIFICATION-DESIGN§9.6) to choose chunked or whole-object storage and the pipeline stages.
- [ ] **BLOB5 — Populate locator replicas.** Every copy placement writes lands in the locator's replica array (or the extent entry's), with one backpointer each. Prerequisite: BLOB1.
- [ ] **BLOB6 — Remove the in-memory blob map.** `DiskEngine.blobs: HashMap<u64, Vec<u8>>` goes away. Prerequisite: BLOB2.
- [ ] **BLOB8 — Tiny objects in the journal and small-object buckets.** Objects up to `INLINE_WRITE_MAX` are written with `WriteInline` and readable at once; a completed write of at most 40 bytes is stored `Inline` in its record; larger ones are packed into small-object blocks in the layout BLOB-D4 selects, journalled by `PackObjects` (JOURNAL-DESIGN§1.3). Prerequisites: BLOB-D4, BLOB2, [JOURNAL9](journal-implementation-plan.md). Acceptance: 10 000 objects of 200 bytes round-trip through reopen, occupy far less than 10 000 × 4 KiB, and each write costs one journal set; a 40-byte write is `Inline` and never packed; a crash after `PackObjects` and before the next checkpoint replays to the same locators.
- [ ] **BLOB9 — Streaming objects.** Create an object in the `Writing` state, append through a per-stream write point in whole buckets, make prefixes durable with `ExtendObject` (or `ChunkListAppend` when chunked), read up to the durable length while writing, and close with `FinalizeObject`, the final length and incrementally computed BLAKE3 hash; after a crash the object stays `Writing` at its last journaled length, readable, and only later bytes are reclaimed; mount never truncates or discards it; it can be resumed or closed, closing without the hash state reading the prefix once (JOURNAL-DESIGN§1.8). A chunked stream's first `ChunkListAppend` sets its content kind and each advances its durable length. Prerequisites: BLOB3, [METADATA8](metadata-implementation-plan.md), [JOURNAL10](journal-implementation-plan.md), [JOURNAL14](journal-implementation-plan.md), [ALLOCATION7](allocation-implementation-plan.md). Acceptance: a 1 GiB stream written with a `Buffered` commit per second, interrupted at random points, reopens at a durable prefix whose bytes and length match what was acknowledged; the same holds for a chunked stream; a stream killed and reopened accepts further appends, and closing it yields the hash of its full content; the extents of an uninterrupted stream are physically sequential.
